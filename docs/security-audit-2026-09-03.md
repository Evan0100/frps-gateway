# frps-gateway 与内网穿透安全审计

> 整改更新：依赖和 Go 工具链已升级，使用 Go 1.26.6 重新执行 `govulncheck ./...` 后两个仓库均无可达漏洞。gateway 已增加 SQLite 用户授权、一次性令牌、3 IP/24h 限制、密钥外置、可信代理解析和机器人停用开关。本文后续内容保留为整改前审计快照；生产网络、真实凭据轮换和云端部署仍需按 `deployment-runbook.md` 完成。

## 1. 结论

截至 2026-09-03，本次静态审查、配置检查和 Go 官方漏洞扫描没有发现“未认证攻击者可直接调用白名单管理 API”或“通过伪造 HTTP 头绕过当前 TCP/HTTP 来源 IP 校验”的明确代码路径，但当前项目和发布包仍不适合按现状直接暴露到公网。

最需要立即处理的风险是：发布包中的 frps 配置没有设置 frpc 认证密钥；构建环境和依赖存在已公开、已有修复版本的漏洞；白名单没有覆盖 UDP 和 XTCP；IP 白名单本身也不能抵御被允许来源、共享 NAT、已失陷终端或 Web 服务自身的远程代码执行漏洞。

本次审查不能证明之前的勒索事件由 frp 引起。要确定入口，必须结合当时实际部署的 frps/frpc 配置、云安全组、Web/系统日志、进程与文件时间线、勒索样本以及受影响主机取证。仓库中的发布配置只能说明存在高风险暴露条件，不能替代现场证据。

## 2. 审查范围与方法

- `frp` 当前分支及未提交的白名单持久化、管理 API、入口拦截和管理页面改动。
- `frps-gateway` 飞书长连接、管理员判断、指令执行和 frps API 客户端。
- `dist/frp-whitelist-windows-amd64-20260903/conf/frps.toml` 发布配置；敏感值只检查是否配置、长度及是否为常见示例值，未写入本报告。
- `go test ./...`、`go vet ./...` 和 Go 官方 `govulncheck`。
- frp 官方安全公告、Go 漏洞数据库、CISA 勒索防护指南和 MITRE ATT&CK。

这不是对正在运行的云服务器进行的渗透测试或主机取证，也没有扫描公网 IP。

## 3. 发现的问题

### SEC-01：发布配置未设置 frpc 认证密钥（严重，立即处理）

证据：发布包的 `conf/frps.toml` 设置了公网控制端口 `bindPort = 7000`，但没有 `auth.token` 或 `auth.tokenSource`。frp 默认认证方式虽然名为 `token`，空 token 仍会参与双方相同的摘要计算，因此使用默认空 token 的陌生 frpc 可以通过登录校验。配置也没有 `allowPorts`，无法限制客户端申请的代理端口范围。

影响：公网攻击者可能把这台 frps 当作未授权隧道基础设施、注册代理或争抢资源。它不等同于直接控制现有内网 Web 服务，但会显著扩大攻击面、资源滥用和代理劫持风险。业务来源白名单只检查访问代理端口的人，不负责认证注册隧道的 frpc，因此不能补偿这个缺口。

处理建议：上线前为 frps 和全部合法 frpc 配置同一个高强度随机 token，优先通过权限受限文件使用 `auth.tokenSource`；轮换任何曾在受感染主机上出现过的旧 token。云安全组仅允许必要来源访问控制端口，并配置最小 `allowPorts`。

### SEC-02：已知依赖和构建工具链漏洞（高，立即升级后重建）

`govulncheck` 的可达符号扫描结果：

| 组件 | 当前版本 | 修复版本 | 影响摘要 |
| --- | --- | --- | --- |
| Go 工具链 | 1.26.5 | 1.26.6 或更新的受支持补丁版 | 命中 `net/url`、`crypto/tls`、`encoding/asn1`、`net/http` 已修复问题 |
| `github.com/gorilla/websocket` | 1.5.0 | 1.5.3 或更新版 | WebSocket 掩码密钥使用弱随机源；frps-gateway 飞书长连接存在可达调用链 |
| `golang.org/x/crypto` | 0.54.0 | 0.56.0 或更新版 | SSH channel 拒绝服务；frps 的可达路径位于可选 SSH Tunnel Gateway |

frp 扫描报告 9 个可达漏洞，frps-gateway 报告 5 个；其中一部分调用链只经过测试代码或可选功能，但 TLS、HTTP 和飞书 WebSocket 路径属于实际运行路径。应升级后重新执行测试、漏洞扫描并重建发布包，不能只替换源码而继续使用旧二进制。

相关官方条目：[GO-2026-6355](https://pkg.go.dev/vuln/GO-2026-6355)、[GO-2026-6354](https://pkg.go.dev/vuln/GO-2026-6354)、[GO-2026-6303](https://pkg.go.dev/vuln/GO-2026-6303)、[GO-2026-6278](https://pkg.go.dev/vuln/GO-2026-6278)、[GO-2026-6218](https://pkg.go.dev/vuln/GO-2026-6218)、[GO-2026-6090](https://pkg.go.dev/vuln/GO-2026-6090)、[GO-2026-6089](https://pkg.go.dev/vuln/GO-2026-6089)、[GO-2026-5972](https://pkg.go.dev/vuln/GO-2026-5972)、[GO-2026-5026](https://pkg.go.dev/vuln/GO-2026-5026)。

### SEC-03：白名单不覆盖全部 frp 流量类型（高，设计边界）

当前覆盖 TCP、HTTPS、TCPMux、STCP/SUDP visitor 的连接入口，以及每个 HTTP vhost 请求。以下流量不能获得同等保护：

- UDP 代理直接按数据报转发，没有调用白名单。
- XTCP 在 visitor 与 provider 之间建立 P2P 连接，业务流量不经过 frps，无法由 frps 按最终来源 IP 拦截。
- STCP/SUDP 校验的是 visitor frpc 主机连接 frps 时的地址，不是该主机后面的最终用户地址。
- 已建立的 TCP 类长连接不会因为删除、过期或进入禁止时段而被主动断开。

如果安全要求是“所有协议必须只有白名单 IP 可访问”，应在当前阶段禁用 UDP、XTCP，并明确 STCP/SUDP 的身份模型；删除白名单后需要同步终止相关活动连接，或接受只对新连接生效的边界。

### SEC-04：全局 IP 白名单不是 Web 漏洞防护（高，架构风险）

当前所有代理共用同一份名单。一个 IP 一旦被允许，就可以访问所有已映射的业务端口，而不是只访问申请的服务。以下情况仍可能导致勒索或入侵：

- 被允许的办公电脑、家庭电脑或跳板机已经中毒。
- 用户位于运营商、公司出口或云代理的共享 NAT 后，其他人可能共享同一个公网 IP。
- 动态公网 IP 在条目过期前被重新分配给其他用户。
- Web 服务存在弱口令、未修补漏洞、任意文件上传、命令执行、反序列化、插件或供应链漏洞。
- Web 服务或管理端口还通过云安全组、公网网卡、路由器端口映射等路径直接暴露，攻击流量绕过 frps。
- 前置 CDN、负载均衡或反向代理使 frps 只能看到代理节点 IP；若把代理节点加入白名单，代理后的所有用户都可能被放行。

应把白名单定位为额外的一层入口限制，而不是 WAF、身份认证、补丁管理、终端安全或网络隔离的替代品。长期方案应改为“用户身份 + 设备身份 + 每个服务单独授权”，例如 VPN/零信任访问代理，并保留应用自身认证和 MFA。

### SEC-05：HTTP `X-Forwarded-For` 可能误导后端安全判断（高，条件性）

frp 的 HTTP vhost 白名单使用真实 TCP `RemoteAddr`，不会直接信任客户端提供的 `X-Forwarded-For`，这一点不会绕过本次白名单。但转发代码会保留客户端原有 `X-Forwarded-For` 后再附加实际来源地址。

如果后端 Web 应用错误地信任列表中的第一个地址，攻击者可以自行填写该请求头，进而绕过后端按 IP 实现的登录限制、限流或审计归因。后端只能信任由最后一个受控代理追加的地址，或由入口代理先删除外部传入的转发头再重建。

### SEC-06：frps 管理面仍依赖 Basic Auth 和网络隔离（高，部署条件）

白名单启用后已经强制要求 webServer 用户名和密码，管理 API 路由也位于认证中间件之后。仍需注意：

- Basic Auth 本身不加密。当前发布配置监听 `127.0.0.1`，本机 HTTP 可以接受；一旦改为跨主机访问，必须使用 HTTPS 或安全隧道。
- 只有单一共享管理账号，没有细粒度角色、MFA、账号锁定或完整失败登录审计。
- 认证失败只有固定延迟，没有基于来源的速率限制。
- `webServer.pprofEnable` 如果开启，pprof 路由注册在认证子路由之外，不应暴露到公网。
- POST/DELETE 使用公共 `BindJSON`，会无上限读取请求体。未认证请求会先被拦截，但持有凭据的误操作或恶意请求仍可能造成内存压力。

保持 `webServer.addr = "127.0.0.1"`，通过本机 gateway 调用；云安全组和主机防火墙不要开放 7500。后续应为白名单 API 增加独立认证、速率限制、请求体上限和失败审计。

### SEC-07：白名单持久化不是防篡改审计（中）

状态文件通过临时文件和原子替换降低部分写入风险，但名单与审计保存在同一个可编辑 JSON 文件中，没有签名、哈希链或远端副本。拥有进程账号或目录写权限的人可以同时修改名单和历史；最近 5000 条覆盖策略也不满足长期取证。

白名单读路径和持久化写入还共用同一互斥锁，写文件、`fsync` 或慢磁盘期间会暂停连接校验。大量管理写入或磁盘异常可能扩大为业务可用性问题。

应限制文件和目录 ACL、以非 root/非管理员账号运行 frps，将审计实时发送到独立日志系统，并为运行日志启用不可变或远端留存。后续可把读路径改为不可变快照，把磁盘写入与连接热路径解耦。

### SEC-08：飞书机器人存在授权范围、重放和审计缺口（高，启用机器人前修复）

- `adminChatID` 模式把指定群内所有用户都视为管理员，并不检查个人 `open_id`；任何被拉入群、账号被盗或误发指令的成员都能增删白名单。
- 代码未校验消息必须明确 @机器人。实际是否只收到 @消息依赖飞书事件订阅行为，不应把平台投递策略当作授权控制。
- 收到事件后立即启动无上限 goroutine，没有并发上限或队列；授权群消息洪泛可能耗尽资源并集中请求 frps。
- `MessageID` 已采集但没有去重。飞书重投可能重复执行“加白”，而重复添加会刷新有效期。
- 执行器没有把飞书用户、消息 ID 和结果写入持久化审计；frps 侧只能看到共享 Basic Auth 账号和本机来源。
- `frps.apiAddr` 没有限制协议和目标。若误配为远程 HTTP，Basic Auth 凭据会以可还原形式传输。

机器人上线前建议只使用 `adminOpenIDs`；要求私聊或显式 @；按 `MessageID` 建唯一索引实现幂等；限制并发和每用户频率；设置最大 TTL；将操作者、原消息、目标 IP、结果和错误持久化；校验 HTTP 只允许回环地址，其他地址必须为 HTTPS。

### SEC-09：文档存在过期且相互矛盾的安全描述（中）

`ROADMAP.md` 仍写有“内存存储”和“e2e 全部通过”；`docs/ip-whitelist-requirements.md` 同时包含“frps 持久化”和“frps 不持久化”，还把 XTCP 描述为受全局白名单控制；`PROJECT.md` 的首期范围仍写“不支持白名单持久化”。这些描述可能导致部署人员错误判断保护范围，应在安全修复时同步更正。

### SEC-10：按 IP 精确匹配缺少运营安全护栏（中）

当前 API 只接受单个 IP，不接受 CIDR，这减少了误放大范围，但没有最大 TTL、条目总数、单人配额、审批或高风险地址提示。`0.0.0.0` 虽然不是可用远端来源，不会形成全网放行，但环回、链路本地、私网、组播等特殊地址仍可被记录；在存在前置代理或复杂路由时容易误配置。

建议增加最大 TTL、条目上限、按服务授权、特殊地址策略、双人审批或至少操作确认，并对长时间和高权限服务单独告警。

## 5. 勒索事件的优先处置

如果受影响主机仍可能在线或尚未完成取证，应优先处置事件，而不是先重新开放 frp：

1. 立即从网络隔离受影响主机和相邻主机，关闭 frps 业务映射端口；保留磁盘快照、内存、日志和时间线证据。
2. 在确认干净的设备上轮换 Web、数据库、操作系统、云平台、frp token、dashboard Basic Auth、飞书 app secret、API key 和备份系统凭据，并撤销现有会话。
3. 对云安全组、主机防火墙、路由器映射和 frpc 配置做完整资产清单，确认是否存在绕过 frp 的直接公网入口，以及是否暴露 RDP、SSH、SMB、数据库、容器 API 或后台管理端口。
4. 从可信镜像重建，不要只删除勒索文件后原地继续运行；修补 Web 框架、插件、操作系统和依赖，检查新增账号、计划任务、服务、启动项、WebShell 和远程工具。
5. 恢复前验证离线或不可变备份，并实际演练恢复。备份账号、存储和生产主机必须隔离，防止攻击者同时加密备份。
6. 重新上线时采用最小端口、每服务授权、MFA、WAF/反向代理、终端检测、集中日志和网络分段；对异常加白、扫描、登录失败和大流量建立告警。

CISA 指出，勒索攻击者经常从暴露且保护不足的远程服务、互联网应用漏洞和失陷凭据进入，并建议关闭不必要的 RDP/SMB 等服务、及时修补、启用 MFA、进行网络分段并保留离线不可变备份，参见 [CISA #StopRansomware Guide](https://www.cisa.gov/stopransomware/ransomware-guide)。MITRE ATT&CK 也明确记录攻击组织曾使用 FRP 转发 RDP 流量，说明 FRP 既是合法工具，也可能被攻击者用于代理和持久访问，参见 [MITRE ATT&CK T1090 Proxy](https://attack.mitre.org/techniques/T1090/)。

## 6. 建议整改顺序

### 上线前必须完成

1. 隔离并完成勒索事件初步取证；确认不存在仍然有效的后门和泄露凭据。
2. 配置并轮换 frpc 强认证；限制 7000 和业务端口的安全组；设置最小 `allowPorts`。
3. 升级 Go、`gorilla/websocket`、`x/crypto`，重跑 `govulncheck`，使用新工具链重建全部二进制。
4. 禁止 UDP、XTCP 和不需要的 KCP/QUIC/SSH Tunnel Gateway；确认没有直达内网服务的旁路公网入口。
5. 保持 dashboard 只监听回环地址，关闭 pprof，限制状态文件和配置文件 ACL。
6. 为被穿透的 Web 服务完成补丁、强认证/MFA、最小权限、上传目录不可执行、数据库隔离和离线备份。

### 下一阶段完成

1. 白名单改为按代理/服务授权，并增加最大 TTL、条目上限和特殊地址策略。
2. 飞书机器人增加个人授权、显式触发、消息去重、速率限制和持久化审计。
3. 连接读路径与持久化写盘解耦；审计发送到独立、不可篡改的远端存储。
4. 为 TCP、HTTP、HTTPS、TCPMux、STCP/SUDP、UDP 和 XTCP 分别建立端到端安全测试，明确每种协议的保护边界。

## 7. 验证结果

- `frps-gateway`: `go test ./...` 通过，`go vet ./...` 通过。
- `frp`: 前序全量单元测试和静态检查通过；Windows Defender 阻止本机构建的 `frps.exe`，TCP/HTTP 专项 e2e 尚未在当前机器补跑。
- `govulncheck`: frp 检出 9 个可达漏洞，frps-gateway 检出 5 个可达漏洞，详见 SEC-02。
- 本次只记录问题和整改建议，没有修改生产配置、认证密钥、云安全组或安全策略。
